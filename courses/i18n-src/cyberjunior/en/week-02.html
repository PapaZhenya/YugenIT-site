Summary

Almost every attack passes through the network, so understanding the network stack is essential groundwork. Data is transmitted through layers; each layer adds its own header.

The TCP/IP stack (simplified)

  • Link layer — transmission within a local segment (MAC addresses).
  • Network layer (IP) — routing between networks by IP address.
  • Transport layer (TCP/UDP) — delivery to a service. TCP is reliable and connection-oriented; UDP is fast and offers no guarantees.
  • Application layer — HTTP, DNS, SMTP.

Ports and the TCP handshake. An IP address points to a host, a port points to a service. TCP connections open via a three-way handshake: SYN → SYN-ACK → ACK.

DNS, and HTTP vs. HTTPS. DNS turns a name into an IP address; phishing and cache poisoning are built around it. HTTP transmits data in plaintext (including logins), while HTTPS adds TLS encryption.

Ports to know by heart: HTTP 80, HTTPS 443, SSH 22, FTP 21, SMTP 25, DNS 53, RDP 3389.

Going deeper

Traffic interception and why HTTPS matters for security

On a shared network (open Wi-Fi), an attacker can "listen" to someone else's traffic. If a site runs on HTTP, logins and data are visible in plaintext. HTTPS encrypts them, making anything intercepted useless. For a security specialist, this is fundamental: unencrypted protocols are a priority target for both attack and defense.

TCP flags and what "port scanning" is

A TCP connection opens with a handshake (SYN → SYN-ACK → ACK). Scanning tools (Nmap) manipulate these steps to determine which ports are open without completing a full connection. Understanding the handshake helps you read logs and recognize scanning — a typical first sign that an attack is being prepared.

The OSI model through a defender's eyes

Each layer has its own class of threats: at the link layer — MAC/ARP spoofing, at the network layer — IP spoofing, at the transport layer — scanning, at the application layer — web attacks. Knowing the layer tells you both the attack vector and where to place defenses. The OSI model isn't just theory — it's a threat map.

Another example: the danger of open Wi-Fi

You're at a cafe, you visit a site over HTTP, and you type in a password. Anyone else on that network with a simple sniffer sees it in plaintext. If the site were on HTTPS, an interceptor would only see encrypted garbage. Takeaway for defense: use HTTPS and a VPN on public networks; for offense, this scenario shows why open protocols are easy prey.

Step-by-step walkthrough: what's visible when you log into a site

  1. The device resolves the site's IP via DNS.
  2. It opens a TCP connection (handshake) on port 443.
  3. TLS encryption is negotiated (for HTTPS).
  4. Encrypted data exchange takes place.
  5. On open Wi-Fi, an outsider sees which IP you connected to, but not the content (for HTTPS).

Mini-project: a map of ports and risks

For a lab machine (or your own PC), build a table:

  • which ports are open (you'll learn to find out with Nmap in module 4 — for now, use known ones);
  • which service sits behind each one;
  • why the open port is risky;
  • whether it's even needed (close anything unnecessary).

This is the first step toward reducing the attack surface.

Key terms

  • TCP/UDP — reliable / fast transport.
  • Port — a "door" to a service (22 SSH, 80 HTTP, 443 HTTPS, 53 DNS).
  • DNS — name → IP.
  • HTTP vs. HTTPS — in the clear / encrypted.
  • TCP handshake — SYN → SYN-ACK → ACK.
  • Sniffer — a traffic interception tool (e.g. Wireshark).

Common mistakes and myths

  • Myth: encryption isn't needed on a private network. An insider threat is still a threat.
  • Mistake: ignoring open ports. Every unnecessary port is a potential entry point.
  • Myth: HTTPS = the site is fully secure. HTTPS protects the channel, not the site itself from vulnerabilities.
  • Mistake: confusing IP and port. IP is the device, port is the service.

Frequently asked questions (FAQ)

  • Is Wireshark a "hacking" tool? No, it's a standard analyzer for diagnostics and defense.
  • Why is HTTPS so important? It encrypts data, making interception worthless.
  • What is port scanning? Checking which services are reachable on a device.
  • Does a VPN protect you on open Wi-Fi? Yes, it encrypts your traffic on top of the network.

Lab work

Part A. Setting up the lab

  1. Install VirtualBox and create a Kali Linux VM.
  2. Configure two adapters: NAT (internet) and Host-Only/Internal (isolated network).
  3. Verify connectivity with ping inside the lab network.

Part B. Capturing HTTP traffic

  1. Start Wireshark on the lab network interface.
  2. Open an HTTP resource with an input form.
  3. Find the three-way handshake (SYN, SYN-ACK, ACK).
  4. Filter for HTTP and find the form data in plaintext.

Part C. Comparing with HTTPS

  1. Repeat the capture while opening an HTTPS resource.
  2. Confirm the content is encrypted.
  3. Record your conclusion: what's visible over HTTP and hidden over HTTPS.

Additional lab work

Part D. Compare HTTP and HTTPS in Wireshark

  1. Capture traffic while logging into an HTTP page with a form — find the data in plaintext.
  2. Repeat with HTTPS — confirm the content is encrypted.
  3. Conclude why this is critical for security.

Part E. Port inventory

  1. Compile a list of standard ports and services.
  2. For three of them, describe why exposing them to the internet is dangerous.
