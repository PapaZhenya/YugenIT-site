The third week of the "Foundations" block teaches you to work confidently in the Linux command line, understand the permissions model, and find traces of events in Linux and Windows system logs.

Module goals

  • Navigate Linux confidently from the command line
  • Understand the permissions model and the principle of least privilege
  • Find and read Linux and Windows system logs

Summary

Infosec tools live in the command line, and investigation begins with logs.

The filesystem and Linux permissions. A tree rooted at /, where everything is a file. Permissions come in three sets (owner/group/others) expressed as rwx. chmod changes permissions, chown changes the owner, sudo grants temporary root privileges. Excessive permissions (777) are a common cause of compromise.

Logs as a source of truth. On Linux — /var/log (auth.log for logins, syslog for the system). On Windows — Event Viewer: Security (logon 4624 success, 4625 failure), System, Application.

Active Directory in a nutshell. In a corporate environment, Windows machines belong to a domain managed by Active Directory — a directory of users, groups, and policies. Understanding AD is critical for Blue Team, because it's exactly what attackers target to take over an entire network.

Going deeper

Users, groups, and root

In Linux, every process has an owner. root is the superuser and can do anything. Regular users are restricted; sudo grants a temporary elevation to root. Attackers are aiming specifically for root ("privilege escalation"), while defense means keeping users at minimal privilege. Understanding this model underlies both attack and defense.

Privilege escalation (in brief)

Attackers often first gain regular-user access, then look for a way to become root: incorrect file permissions, vulnerable programs with elevated flags, weak sudo settings. The defender's job is not to leave these loopholes open. In this course, we look at this conceptually and only in the lab.

Processes, services, and startup

A system is a collection of running processes and services. Malware often disguises itself as a system process and adds itself to startup to survive a reboot. That's why knowing how to view the process list and startup items is a basic investigative skill (useful in weeks 9–10).

Another example: the danger of 777 permissions

A developer set a config file's permissions to 777 "to make it work." Now any user on the system can read and modify it — including the secrets inside it. An attacker who gains even low-level access can tamper with the file and escalate privileges. Takeaway: permissions aren't a formality — they're an attack surface. The correct approach is minimally necessary permissions.

Step-by-step walkthrough: finding failed logins in a log

  1. Open /var/log/auth.log.
  2. Filter for lines containing Failed password: grep "Failed password" auth.log.
  3. Count them: add | wc -l.
  4. Find which IPs the attempts came from: grep "Failed password" auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn.
  5. Many attempts from one IP → a likely password brute-force.

Key terms

  • root — the Linux superuser.
  • sudo — temporary privilege elevation.
  • rwx / chmod — access permissions and how to change them.
  • auth.log / syslog — Linux logs.
  • Event ID 4624/4625 — logon/failure on Windows.
  • Privilege escalation — obtaining higher-level access.
  • Startup (autorun) — a mechanism that launches at boot (a common persistence spot).

Common mistakes and myths

  • Myth: no one reads the logs, so they're pointless. Logs are the primary source of truth during an investigation.
  • Mistake: setting 777 "to make it work." That's an open door.
  • Myth: you need root for everything. Quite the opposite — work with the minimum necessary permissions.
  • Mistake: trusting history -c. Traces often remain in other logs.

Frequently asked questions (FAQ)

  • Do I really need to know Linux? Yes, it's the core tool of a security specialist.
  • Why read logs by hand if there's a SIEM? Understanding logs is foundational; a SIEM only automates it.
  • Which matters more — Linux or Windows? Both: servers are often Linux, corporate environments run Windows/AD.
  • What is privilege escalation? Gaining higher access than was originally granted.

Module cheat sheet

  • Navigation: pwd ls -la cd cat less grep head tail.
  • Permissions: chmod, the rwx model (owner/group/others), 777 — dangerous.
  • Escalation: sudo; an attacker's goal is root.
  • Logs: /var/log/auth.log, syslog; Windows — Event Viewer (4624/4625).
  • Counting failed logins: grep "Failed password" auth.log | wc -l.

Lab work

Part A. Navigation and files

  1. Learn: pwd, ls -la, cd, cat, less, head, tail, grep.
  2. Create a directory and files, practice moving around and viewing them.

Part B. Access permissions

  1. Create a user and a file; change permissions with chmod.
  2. Check what another user can and can't do.
  3. Show why 777 permissions on a file with a secret are dangerous.

Part C. Reading logs

  1. Find successful and failed logins in /var/log/auth.log using grep.
  2. Write a one-liner that counts failed logins.
  3. On a Windows VM, find events 4624 and 4625 in Event Viewer.

Additional lab work

Part D. Analyzing Windows logs

  1. On a Windows VM, open Event Viewer → Security.
  2. Find events 4624 (successful logon) and 4625 (failure).
  3. Determine what a password brute-force would look like in these events.

Part E. Processes and startup

  1. Display the process list (ps aux on Linux).
  2. Check what starts automatically.
  3. Explain why malware tries to get into startup.
