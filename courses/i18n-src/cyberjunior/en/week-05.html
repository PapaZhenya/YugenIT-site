What it looks like (diagram)

SQL injection — input treated as code:

Normally:  SELECT * FROM users WHERE login='admin' AND pass='1234'
Injection: login = admin'--
          SELECT * FROM users WHERE login='admin'--' AND pass='...'
          (everything after -- is ignored -> login without a password)

XSS — someone else's script running in the victim's browser:

Comment field:  <script>stealCookie()</script>
-> gets saved on the site -> runs for EVERY visitor

Summary

The OWASP Top 10 is a regularly updated list of the most critical web application risks, maintained by the OWASP community. It's a priority list — a starting point for both defenders and attackers.

SQL injection. Occurs when input reaches a SQL query without being processed. Example: ' OR '1'='1 in a login form makes the condition always true. The cause is string concatenation instead of parameterized queries. Defense: prepared statements, validation, minimal database privileges.

Cross-site scripting (XSS). Injected JavaScript runs in the victim's browser. Reflected XSS lives in a link; Stored XSS is saved on the server and hits every visitor. Defense: output escaping, CSP, the HttpOnly cookie flag.

Broken authentication. No protection against brute-forcing, predictable tokens, default passwords. Defense: MFA, brute-force protection, secure session tokens.

Insecure configuration. Open admin panels, default accounts, verbose error messages, unnecessary services. The most common vulnerability. Defense: hardening, configuration checks, minimalism.

Deeper dive

Why injections happen (and how to defend against them)

The root cause is mixing data and code: user input ends up as part of a command. The defense is parameterized queries (input is passed as data, not as code), input validation, and minimal database privileges. This rule extends beyond SQL: mixing data and commands is dangerous in general (command injection, LDAP injection, etc.).

Reflected, Stored, and DOM XSS

There are three types of XSS. Reflected — the script lives in a link and fires for whoever clicks it. Stored — the script is saved on the server (e.g. in a comment) and hits every visitor — the most dangerous type. DOM-based — runs in the browser because of unsafe JavaScript. The defenses are shared: output escaping, Content Security Policy, the HttpOnly cookie flag.

The rest of the OWASP Top 10 (overview)

Besides injection and XSS, the list includes: broken access control, cryptographic failures, security misconfiguration, vulnerable components (outdated libraries), identification/authentication failures, request forgery (SSRF), and more. The common thread is recurring, typical mistakes that both attackers and defenders start with.

One more example: stealing a session via Stored XSS

An attacker leaves a script in a comment that sends the visitor's cookie to their own server. Everyone who opens the page unknowingly "hands over" their session — the attacker logs in as them without a password. Defense: escape output (the script won't execute), set the HttpOnly cookie flag (JavaScript can't read it). One example — an attack and two defenses at once.

Step-by-step walkthrough: finding SQLi in the lab

  1. Deploy a training application (DVWA/Juice Shop) in an isolated environment.
  2. Find a field that talks to the database (search/login).
  3. Enter a single quote ' — a database error points to a vulnerability.
  4. Test the classic authentication-bypass payload.
  5. Document the finding: where, how to reproduce it, the risk, and how to fix it (parameterization).
⚠️ Training applications in an isolated lab only. Never real sites.

Mini-project: vulnerability cards

After working through the training labs, put together "finding cards" (the way a real pentest report would):

  • the vulnerability's name and where it was found;
  • steps to reproduce it;
  • risk rating (low/medium/high);
  • remediation recommendation;
  • a screenshot as proof.

A set of cards is a strong portfolio piece.

Key terms

  • OWASP Top 10 — a list of critical web risks.
  • SQL injection — injecting SQL through input.
  • XSS — injecting JavaScript (reflected/stored/DOM).
  • Parameterized query — a defense against injection.
  • CSP / HttpOnly — measures against XSS.
  • DVWA / Juice Shop — training vulnerable applications.

Common mistakes and myths

  • Myth: injections are about "filtering bad words". Real protection is parameterization, not blacklists.
  • Mistake: treating stored and reflected XSS as the same. Stored is more dangerous — it hits everyone.
  • Myth: HTTPS protects against SQLi/XSS. No — these are application vulnerabilities, not channel vulnerabilities.
  • Mistake: testing on other people's sites. Training applications in a lab only.

Frequently asked questions (FAQ)

  • How do I defend my own site? Parameterization, escaping, keeping components updated, hardening.

Lab work

⚠️ Legal framework. All actions must take place only in an isolated lab or on explicitly authorized platforms. Attacking someone else's systems without permission is illegal.

Part A. Environment setup

  1. Deploy DVWA or OWASP Juice Shop locally (Docker or a ready-made VM).
  2. For DVWA, set the security level to "low".
  3. Set up an intercepting proxy (Burp Suite Community or OWASP ZAP).

Part B. SQL injection

  1. Find a field that talks to the database (search or login).
  2. Enter a single quote ' and observe the database error.
  3. Apply an authentication-bypass payload and record the result.
  4. In the proxy, see how the input changed the SQL query.

Part C. XSS

  1. Find a field whose input gets displayed on the page.
  2. Inject a harmless test script (alert).
  3. Determine the type: reflected or stored.
  4. Describe how an attacker would steal the session cookie.

Part D. Authentication and configuration

  1. Try default credentials (admin/admin).
  2. Check for brute-force protection.
  3. Find an exposed service page or a verbose error message.

Part E. Writing up findings

  1. Fill out a card for each vulnerability: name, location, how to reproduce, risk, how to fix.
  2. Attach evidence (request/response screenshots).
