This module of the "Defense" block covers network monitoring tools — IDS/IPS and SIEM — along with the principles of network segmentation and DMZs for containing attacks.

Summary

Walls don't protect you if nobody's watching them. This module is about detection.

IDS, IPS, and SIEM. An IDS notices suspicious activity and raises a signal; an IPS also blocks it. SIEM collects logs from every system, correlates events, and raises alerts — it's the SOC analyst's workbench. Logs are useless until someone reads them; SIEM turns the stream into signals.

Segmentation and DMZ. A network is divided into zones with controlled transitions. Public services are placed in a DMZ — a buffer between the internet and the internal network. A breached DMZ doesn't grant access to the whole infrastructure.

From event to alert. Dozens of "Failed password" entries from a single IP within a minute is almost certainly a brute-force attempt; an alert rule is configured to catch exactly this pattern.

Deeper dive

IDS vs. IPS

An IDS (intrusion detection system) notices suspicious activity and raises a signal. An IPS additionally blocks it. An IDS is a "camera with an alarm"; an IPS is a "camera + automatic lock." The choice depends on whether you're ready for automatic blocking (with its risk of false positives).

What SIEM is and why a SOC analyst needs it

SIEM collects logs from every system into one place, correlates events across sources, and raises alerts. It's the SOC analyst's workbench: raw logs are useless until someone pulls them together. Knowing how to write an alert rule (for example, for password brute-forcing) is a key skill.

Segmentation and DMZ

Dividing a network into zones with controlled transitions. Public services are placed in the DMZ — a buffer between the internet and the internal network. If an attacker breaches the DMZ, they don't get the whole network at once. This is the principle of containment and defense-in-depth applied at the network level.

One more example: why "we have logs, but they don't help"

A company had been writing logs for years, but nobody looked at them. When a breach happened, it turned out the traces were there — nobody had pulled them together or noticed. After deploying SIEM with rules, the same events became alerts, and the next attack was caught within minutes. The moral: the value isn't in the logs themselves, but in collecting, correlating, and responding to them.

Step-by-step walkthrough: from event to alert

  1. The source (a server) writes login logs.
  2. SIEM collects them in real time.
  3. A rule counts failed logins from a single IP over an interval.
  4. Threshold exceeded → SIEM raises a "brute-force" alert.
  5. The analyst sees the alert and checks the context (IP, user, time).
  6. Decision: block the IP, escalate, or close it as a false positive.

Mini-project: a brute-force detection rule

In a training SIEM (Wazuh/ELK) or on paper:

  • describe which log fields you need (IP, user, result, time);
  • write the rule: "> N failed logins from one IP within M minutes → alert";
  • think through how to tell an attack apart from an employee's forgotten password (thresholds, whitelist);
  • describe the analyst's response to the alert.

Key terms

  • IDS / IPS — detection / detection+blocking.
  • SIEM — log collection and correlation, alerts.
  • SOC — security operations center.
  • Alert — a signal about a suspicious event.
  • DMZ — a buffer zone for public services.
  • Segmentation — dividing a network into zones.

Common mistakes and myths

  • Myth: collecting logs = ensuring security. Logs need to be correlated and acted on.
  • Mistake: overly "noisy" rules. A flood of false alerts dulls vigilance.
  • Myth: IPS is always better than IDS. Automatic blocking can cut off legitimate traffic.
  • Mistake: a flat network with no segmentation. Compromising one node opens up everything.

Frequently asked questions (FAQ)

  • What does a SOC analyst do? Watches SIEM alerts, investigates, responds — the goal of this course.
  • IDS or IPS? IDS is safer to start with; IPS is for when you're ready for automatic blocking.
  • Why would I need a DMZ at home? At home it's simpler — a guest network; a DMZ matters for organizational servers.
  • Where do I start with SIEM? With one log source and one simple rule.

Module cheat sheet

  • IDS detects, IPS blocks. SIEM aggregates logs and raises alerts.
  • Logs are useless without correlation and response.
  • DMZ + segmentation = limiting the spread.
  • A classic alert: password brute-forcing (many Failed entries from one IP).
  • Less "noise" means a sharper response.

Lab work

Part A. Deploying SIEM

  1. Deploy a lightweight SIEM (Wazuh or ELK).
  2. Connect a log source — a Linux VM.
  3. Confirm events are coming in.

Part B. Generating and detecting an attack

  1. Generate a series of failed SSH logins.
  2. Find the events in SIEM and identify the important fields (IP, user, time).

Part C. Alert rule

  1. Configure a rule: N failed logins from one IP within a short time → alert.
  2. Verify it fires.
  3. Describe how the alert would help an analyst in a real SOC.

Additional lab work

Part D. Deploy a mini-SIEM

  1. Spin up a training SIEM (Wazuh or ELK) in the lab.
  2. Connect a log source (a Linux VM).
  3. Confirm events are coming in.

Part E. Test your alert

  1. Generate a series of failed logins.
  2. Set up an alert rule and get it to fire.
  3. Work out which fields matter for an analyst.
