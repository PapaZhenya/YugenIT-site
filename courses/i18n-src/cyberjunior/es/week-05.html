Cómo se ve (esquema)

Inyección SQL — entrada tratada como código:

Normalmente:  SELECT * FROM users WHERE login='admin' AND pass='1234'
Inyección: login = admin'--
          SELECT * FROM users WHERE login='admin'--' AND pass='...'
          (todo después de -- se ignora -> inicio de sesión sin contraseña)

XSS — un script ajeno en el navegador de la víctima:

Campo de comentario:  <script>robar_cookie()</script>
-> se guarda en el sitio -> se ejecuta en CADA visitante

Apuntes

El OWASP Top 10 es una lista actualizada periódicamente con los riesgos más críticos de las aplicaciones web, elaborada por la comunidad OWASP. Es la prioridad: por dónde empezar tanto el defensor como el atacante.

Inyección SQL (Injection). Ocurre cuando la entrada llega a una consulta SQL sin procesar. Ejemplo: ' OR '1'='1 en un formulario de login hace que la condición sea siempre verdadera. La causa es la concatenación de cadenas en vez de consultas parametrizadas. Defensa: sentencias preparadas, validación, permisos mínimos de la base de datos.

Cross-Site Scripting (XSS). El JavaScript inyectado se ejecuta en el navegador de la víctima. Reflected vive en un enlace; Stored se guarda en el servidor y afecta a todos. Defensa: escape de salida, CSP, flag HttpOnly en las cookies.

Autenticación rota. Sin protección contra fuerza bruta, tokens predecibles, contraseñas por defecto. Defensa: MFA, protección contra brute-force, tokens de sesión seguros.

Configuración insegura. Paneles de administración abiertos, cuentas estándar, errores detallados, servicios innecesarios. La vulnerabilidad más frecuente. Defensa: hardening, verificaciones de configuración, minimalismo.

Profundizando en el tema

Por qué surgen las inyecciones (y cómo defenderse)

La raíz es la mezcla de datos y código: la entrada del usuario llega a una consulta como parte del comando. La defensa son las consultas parametrizadas (la entrada se trata como datos, no como código), la validación de entrada, los permisos mínimos de la base de datos. Esta regla es más amplia que SQL: cualquier mezcla de datos y comandos es peligrosa (inyecciones de comandos, LDAP, etc.).

Reflected, Stored y DOM XSS

Tres tipos de XSS. Reflected — el script está en un enlace, se activa en quien hace clic en él. Stored — el script se guarda en el servidor (en un comentario) y afecta a todos los visitantes — el más peligroso. DOM-based — se ejecuta en el navegador debido a JavaScript inseguro. La defensa es común: escape de salida, Content Security Policy, flag HttpOnly en las cookies.

El resto del OWASP Top 10 (panorama general)

Además de las inyecciones y XSS, la lista incluye: control de acceso roto, fallos criptográficos, configuración insegura, componentes vulnerables (bibliotecas antiguas), errores de identificación/autenticación, falsificación de solicitudes (SSRF) y otros. La idea general es que son errores típicos y recurrentes por los que empiezan tanto el atacante como el defensor.

Otro ejemplo: cómo se roba una sesión mediante Stored XSS

El atacante deja en un comentario un script que envía la cookie del visitante a su propio servidor. Cada persona que abre la página, sin querer, «entrega» su sesión — el atacante inicia sesión con su identidad sin necesitar la contraseña. Defensa: hacer escape de la salida (el script no se ejecutará), poner el flag HttpOnly en la cookie (JavaScript no podrá leerla). Un solo ejemplo — a la vez un ataque y dos medidas de defensa.

Análisis paso a paso: búsqueda de SQLi en el laboratorio

  1. Despliega la aplicación de práctica (DVWA/Juice Shop) en un entorno aislado.
  2. Encuentra un campo que consulte la base de datos (búsqueda/login).

  • XSS — inserción de JavaScript (reflected/stored/DOM).
  • Consulta parametrizada — defensa contra inyecciones.
  • CSP / HttpOnly — medidas contra XSS.
  • DVWA / Juice Shop — aplicaciones vulnerables de práctica.

Errores y mitos frecuentes

  • Mito: las inyecciones se evitan «filtrando palabras malas». La defensa real es la parametrización, no las listas negras.
  • Error: considerar iguales el XSS stored y el reflected. El stored es más peligroso — afecta a todos.
  • Mito: HTTPS protege contra SQLi/XSS. No, son vulnerabilidades de la aplicación, no del canal.
  • Error: probar en sitios ajenos. Solo aplicaciones de práctica en el laboratorio.

Laboratorio

⚠️ Marco legal. Todas las acciones — solo en un laboratorio aislado o en plataformas explícitamente autorizadas. Atacar sistemas ajenos sin permiso es ilegal.

Parte A. Preparación del entorno

  1. Despliega DVWA u OWASP Juice Shop localmente (Docker o una VM ya preparada).
  2. Para DVWA, configura el nivel de seguridad en «low».
  3. Configura un proxy interceptor (Burp Suite Community u OWASP ZAP).

Parte B. Inyección SQL

  1. Encuentra un campo que consulte la base de datos (búsqueda o login).
  2. Introduce una comilla simple ' y observa el error de la base de datos.
  3. Aplica la carga de evasión de autenticación y documenta el resultado.
  4. En el proxy, observa cómo la entrada modificó la consulta SQL.

Parte C. XSS

  1. Encuentra un campo cuya entrada se muestre en la página.
  2. Inserta un script de prueba inofensivo (alert).
  3. Determina el tipo: reflected o stored.
  4. Describe cómo un atacante robaría la cookie de sesión.

Parte D. Autenticación y configuración

  1. Prueba credenciales estándar (admin/admin).
  2. Comprueba la protección contra fuerza bruta.
  3. Encuentra una página de servicio abierta o un error detallado.

Parte E. Documentación de hallazgos

  1. Completa una ficha para cada vulnerabilidad: nombre, dónde, cómo reproducirla, riesgo, cómo corregirla.
  2. Adjunta evidencias (capturas de pantalla de la solicitud/respuesta).
