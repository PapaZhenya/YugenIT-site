This module explains why data transmission is described in layers, breaks down the TCP/IP and OSI models, and shows how the correspondence between them helps you quickly pinpoint where a network has broken.

Introduction

You've already seen live data exchange and worked through addressing. Now let's put things in order in your head. Networks are described using layers — and this isn't dry theory for theory's sake, but a working tool that saves hours when tracking down faults. When a specialist says "the problem is at layer three," they instantly narrow the search. Let's learn to do the same.

Summary

Why networks are split into layers

The task of "transmitting data" is enormous: you need to physically carry a signal, find a path between networks, ensure reliability, and show a person a web page. Dumping it all into one pile is impossible. So the task is split into layers, where each one is strictly responsible for its own part and doesn't meddle with anyone else's.

It's like package delivery at a warehouse: one worker packs the box, another writes the address, a third loads it onto the truck, a fourth drives it. Everyone handles their own job. If the package doesn't arrive — it's immediately clear who to ask. Layers in a network work exactly the same way, simplifying both development (you can improve one layer without breaking the others) and diagnostics (a problem is easy to localize).

The TCP/IP model: four working layers

This is the model the internet actually runs on. It has four layers, from bottom to top:

  • Data Link — transmission within a single local segment of the network, using MAC addresses. Responsible for delivery "to the next-door device" within a LAN.
  • Network — delivery between different networks, using IP addresses. This is where "across half the world" routing happens.
  • Transport — getting data to the right program. This is home to TCP (reliable, with acknowledgment of every piece) and UDP (fast, no guarantees — for video and games).
  • Application — what you use directly: the web (HTTP/HTTPS), email, DNS.

Each layer uses the services of the layer below and provides services to the layer above. You work at the application layer, while everything else happens invisibly underneath.

The OSI model: seven layers for study

OSI is a more detailed, "reference" model made up of seven layers: physical, data link, network, transport, session, presentation, application. In practice, networks run on TCP/IP, but OSI is kept as a shared language: it's more detailed and convenient for discussing exactly where a problem occurred.

You don't need to memorize all seven by heart on day one. It's enough to understand the logic: at the bottom is "hardware and signal," in the middle are "addresses and delivery," and at the top are "applications and data for a human." You'll come back to the details of the upper layers (session, presentation) when you actually need them.

How the two models correspond to each other

The models aren't competitors — they're about the same thing, just at a different level of detail. Roughly speaking: the TCP/IP application layer covers about the three upper OSI layers (application, presentation, session); transport and network match up almost one to one; and the TCP/IP data link layer covers the OSI data link and physical layers.

Practical takeaway: if you understand the four TCP/IP layers, you already have your bearings in the seven OSI layers — the latter just spells out some layers in more detail.

Encapsulation: how data gets wrapped in headers

Remember the "data inside, labels on the outside" image from module 1? Now it becomes precise. As data travels "down" through the layers, each layer adds its own header — this is encapsulation. Application data is wrapped by the transport header (becoming a segment), then by the network header (becoming a packet), then by the data link header (becoming a frame). On the receiving side, everything is unwrapped in reverse order — headers are stripped off layer by layer, until only the clean data remains.

Hence the different names for the same thing at different layers: at the transport layer — segment, at the network layer — packet, at the data link layer — frame. This often confuses beginners, but now you know: it's just data with a different number of "labels."

How layers help when things break

The main practical benefit of the model is the "bottom-up" diagnostic method. When a network isn't working, you don't poke around at random — you go layer by layer: is there a physical signal/cable (bottom) → is the IP address correct (network) → does it reach the right program (transport/application). Wherever it breaks off — that's where the problem is.

We'll put this into real practice in module 8, which is dedicated to diagnostics. For now, just remember: the layer model is a map that lets you find faults quickly and without panic.

Digging deeper

What each layer does (a bit more detail)

  • Physical (OSI): the actual signals — voltage on a wire, light in fiber optics, radio waves.
  • Data Link: frames and MAC addresses, delivery "to the next-door device" within a segment.
  • Network: IP addresses and "across the world" routing.
  • Transport: ports, reliability (TCP) or speed (UDP).
  • Application: the protocols a person actually sees (HTTP, DNS, email).

TCP in more detail: why it's "reliable"

TCP guarantees delivery using several techniques: it numbers pieces so they can be reassembled in order; it waits for acknowledgment of receipt of each one; it resends anything lost; and it regulates speed so as not to overload the connection. All of this comes at the cost of some overhead. That's why TCP is used wherever integrity matters (websites, files, email).

UDP in more detail: why it's "fast"

UDP simply sends data without acknowledgments or resends. If a packet gets lost — oh well, the next one matters more. This is ideal for live video, voice, and games: it's better to drop a frame than to wait and stutter. The choice between TCP and UDP is a choice between "reliable, but cautious" and "fast, but no guarantees."

Worked example: what happens at each layer when opening a website

Let's take opening example.com and walk through the TCP/IP layers top to bottom (how data is prepared for sending):

Application: the browser forms an HTTP request, "give me the page." Transport: TCP splits the request into segments and tags them so they can later be reassembled in order and checked that nothing was lost; it adds the destination port (443). Network: IP adds addresses — where from and where to (your IP and the server's IP); now it's a packet, which can be routed between networks. Data Link: a frame with MAC addresses is added for delivery to the nearest device (the router).

On the server, everything is unwrapped in reverse order: frame → packet → segment → and at the top the server reads the clean HTTP request and prepares a response. The response makes the same trip back to you.

Another example: identify the layer of the fault

  • "Cable unplugged, no light on" → physical.
  • "No IP received / incorrect IP" → network (check DHCP).
  • "IP pings, but the site doesn't load by name" → application (DNS).
  • "Connection keeps dropping, speed fluctuates" → often transport/data link.

Being able to name the layer immediately halves the search for the cause.

Step-by-step walkthrough: a message passes through all the layers

We send an HTTP request from top to bottom:

  1. Application: the browser writes "GET /page."
  2. Transport: TCP adds a port (443), numbers the segment.
  3. Network: IP adds the sender's and recipient's addresses — it's now a packet.
  4. Data Link: a frame with a MAC address is added, addressed to the nearest router.
  5. The frame goes out onto the network; at each router the data link header is updated, while the IP header stays the same.
  6. On the server, everything is stripped away bottom to top, and the application reads the clean request.

Key terms

  • Layer — a logical layer responsible for its part of the network's work
  • TCP/IP model — the practical 4-layer model that the internet runs on
  • OSI model — the reference 7-layer model, a shared language for describing networks
  • Encapsulation — adding a header at each layer as data moves downward
  • Segment — data with a transport header (TCP/UDP layer)
  • Packet — data with a network (IP) header
  • Frame — data with a data link header (MAC addresses)
  • TCP / UDP — transport protocols: reliable with acknowledgment / fast with no guarantees

Common mistakes and myths

  • Mistake: memorizing the 7 OSI layers on day one. First understand the logic and the 4 TCP/IP layers.
  • Myth: OSI and TCP/IP are competitors. They're the same thing, at different levels of detail.
  • Mistake: confusing segment/packet/frame. It's the same data with a different number of headers.
  • Myth: layers are an abstraction with no practical use. On the contrary, they're the main diagnostic tool.
  • Mistake: assuming TCP is always better than UDP. For video and games, UDP is actually preferable.

Frequently asked questions (FAQ)

  • Why two models? OSI is a detailed "map for discussion," TCP/IP is the internet's working model.
  • Do I need to memorize the 7 layers? No. Master the logic and the 4 TCP/IP layers — that's enough for a long time.
  • Why is the same data called different things? Because of the number of headers: segment/packet/frame are stages of the same encapsulation.
  • Is TCP always better than UDP? No. For video/games, UDP is preferable.
  • At which layer does Wi-Fi "live"? Mainly at the data link and physical layers — the medium is just radio.

Module cheat sheet

  • TCP/IP = 4 layers: data link (MAC) → network (IP) → transport (ports) → application.
  • OSI = 7 layers (more detailed, a shared language).
  • Encapsulation: data → segment → packet → frame.
  • TCP — reliable (acknowledgments, resending). UDP — fast (no guarantees).
  • Diagnostics are done bottom to top, layer by layer.

Lab work

Part A. Break down opening a website by layer

  1. Take the example of opening a website from module 1.
  2. Write out what happens at each of the 4 TCP/IP layers when sending the request.
  3. Map these 4 layers to the layers of the OSI model.

Part B. Find the layers in real traffic

  1. In Wireshark, open a single captured packet and expand its structure.
  2. Find the layers in it: Ethernet (data link), IP (network), TCP/UDP (transport), data (application).
  3. Mark where in the packet the MAC addresses are, and where the IP addresses are.

Part C. Encapsulation on paper

  1. Draw a diagram of encapsulation: how application data turns into a segment → packet → frame.
  2. Label which header is added at each step.

Part D. Identify the layer of the problem

  1. For three situations, determine the likely layer: (a) cable unplugged, (b) incorrect IP, (c) the site doesn't open by name but does open by IP.
  2. Justify each answer.

Additional labs

Part E. TCP vs UDP in traffic

  1. In Wireshark, find TCP packets and UDP packets (for example, DNS is usually over UDP).
  2. Compare whether TCP has acknowledgments (ACK) while UDP doesn't.
  3. Draw a conclusion about why TCP is used for websites.

Part F. Build encapsulation by hand

  1. Take a sheet of paper and "pack" a message layer by layer, labeling each added header.
  2. Then "unpack" it on the receiving side, from bottom to top.
