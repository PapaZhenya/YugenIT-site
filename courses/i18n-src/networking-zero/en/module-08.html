This module teaches you to systematically troubleshoot network problems using the "bottom-up" method, working with four basic diagnostic tools: ping, tracert/traceroute, ipconfig/ip, and nslookup.

Module goals

  • Master the core network diagnostic tools
  • Learn to search for a fault systematically, not at random
  • Apply the "bottom-up" diagnostic method, layer by layer
  • Be able to localize typical problems
  • Read the output of the ping and traceroute commands

Introduction

Sooner or later, every network "stops working" at some point. A beginner panics in that moment and pokes around at random: rebooting everything, swapping cables, calling the provider. A specialist acts differently — following a system, ruling out options step by step. This module gives you that system and a simple set of commands used every single day.

Summary

Your diagnostic toolkit

Four commands cover most everyday situations, and they're available on any system:

  • ping — "are you alive?". Sends a short request to a host and waits for a reply. If there's a reply — the host is reachable and the network to it is working.
  • tracert / traceroute — "where's the break?". Shows the path to a host hop by hop and at which step the connection is lost.
  • ipconfig / ip — "what about my own setup?". Shows your address, mask, gateway, and DNS.
  • nslookup — "do names still work?". Checks whether DNS responds and whether it correctly resolves names into addresses.

Master these four, and you'll already cover the vast majority of network problems.

The "bottom-up" method, layer by layer

Remember the layers from module 3? Diagnostics are done exactly along them, from simple to complex:

  1. Physical layer. Is the cable plugged in, is Wi-Fi connected, are the indicator lights on?
  2. Your own settings. Is there a proper IP (ipconfig/ip)? Is it not "self-assigned" (169.254.x.x = DHCP failed)?
  3. Gateway. Does the router's address respond to ping? If not — the problem is inside the local network.
  4. Getting out to the internet. Does an external IP respond to ping (for example, 8.8.8.8)? If yes, but sites don't open — the issue isn't connectivity, it's DNS.
  5. DNS. Does nslookup work? If names aren't resolving — there's the cause.
  6. The site/service itself. Maybe the problem isn't on your end but on the server's.

Wherever the chain breaks — that's where the root of the problem is. This order saves a huge amount of time.

How to read ping

ping shows whether replies got through and how long they took. It's useful to look at three things: whether there are any replies at all (if it's "request timed out" — the host is unreachable or is blocking ping), response time (large delays mean the network is congested or far away), and loss (if part of the replies are lost, the connection is unstable).

An important nuance: some hosts deliberately don't respond to ping for security reasons, so a missing reply doesn't always mean something's broken. But as a first quick test, ping is indispensable.

How to read traceroute

traceroute/tracert outputs a list of hops — the routers along the path to the destination — and the time to each one. It's simple to read: go from top to bottom and see up to which hop everything's fine, and where losses or "asterisks" (no reply) begin.

If the break is at the first or second hop, the problem is with you or your router. If it's further along, it's with the provider — the problem isn't on your side. This helps you figure out who to actually call: fix it yourself or contact the provider.

The three most common causes of "no internet"

Experience shows that three things are usually to blame. First — DHCP/address problems: the device didn't get a proper IP (that same 169.254.x.x). Second — a wrong or unreachable gateway: locally everything seems fine, but it doesn't reach the outside. Third — DNS not working: everything pings fine by IP, but sites don't open by name.

Check these three first — and most problems will be solved in a couple of minutes. This is exactly why the "bottom-up" method is so effective: it leads you straight to these typical causes.

Diagnostic discipline: change one thing at a time

Golden rule: change one thing at a time and check the result. If you rebooted the router, changed the cable, and switched DNS all at once — and it started working, you won't know what actually helped, and next time you'll be guessing again. Change one thing at a time, record what you checked and what changed. This is what separates a master from a "random poker," and it will serve you in any technical field, not just networking.

Going deeper

What ping replies mean

  • "Reply from …" — the host is reachable; check the time (ms).
  • "Request timed out" — no reply: the host is unreachable, overloaded, or blocking ping.
  • "Destination host unreachable" — no route: often a gateway/settings problem.
  • Varying times and losses across a series — an unstable connection.

Useful command flags

ping -t (Windows) / ping without a count (Linux) — continuous ping, handy for catching "intermittent" drops. ping -n 100 — send 100 requests and assess loss. tracert -d — don't resolve addresses to names (faster). Knowing a couple of flags speeds up diagnostics noticeably.

Logs and indicators

Don't forget the simple stuff: the lights on the router and network adapter say a lot (no link — no cable/signal). And the router's settings often have an event log — showing reboots, provider issues, device connections. Sometimes the answer is right there on the surface.

Worked example: a site won't open — finding the cause

Situation: the browser says the site is unavailable. Let's follow the method.

The cable/Wi-Fi is in place, the indicators are lit — the physical layer is fine. ipconfig shows a proper address, 192.168.1.20, and gateway 192.168.1.1 — settings are present. We ping the gateway 192.168.1.1 — it replies, so the local network works. We ping 8.8.8.8 — it replies too! So there's a way out to the internet, connectivity isn't the issue.

That leaves DNS. We run nslookup example.com — an error, the name doesn't resolve. There's the cause: the connection works, but names aren't turning into addresses. It's fixed by changing the DNS server in the settings. Notice: we didn't reboot everything in a row — in five steps we pinpointed the root exactly.

Another example: internet that's "there, then not"

Intermittent drops are the most annoying kind. I run ping -t 8.8.8.8 and leave it for 10 minutes. I see periodic "request timed out" messages and spikes in response time — meaning the connection is unstable (not "completely broken"). Next I narrow it down: is it the same up to the gateway? If it's stable up to the gateway but not beyond, the problem is with the provider or on the channel. Continuous ping is your best friend in cases like this.

Step-by-step walkthrough: "not a single site is loading for me"

  1. I check the lights/network icon — there's a connection.
  2. ipconfig → address 169.254.1.7. Ah, that's a telltale sign: DHCP failed.
  3. So the problem is at the settings step — the device didn't get an address.
  4. I restart the connection / check DHCP on the router.
  5. Now the address is proper, 192.168.1.20, and there's a gateway.
  6. ping to the gateway and to 8.8.8.8 both go through; the site opens. Done.

Notice: I found the cause at step two, without touching everything in a row.

Key terms

  • ping — a command for checking host reachability
  • traceroute / tracert — a command that shows the path to a host hop by hop
  • ipconfig / ip — a command for viewing your own network settings
  • nslookup — a command for checking that DNS works
  • The "bottom-up" method — diagnostics by layer, from the physical layer to the application
  • Latency — a host's response time, shown by ping
  • Packet loss — the share of replies that didn't arrive — a sign of an unstable connection

Common mistakes and myths

  • Mistake: changing everything at once. Change one thing at a time and check — otherwise you won't know what helped.
  • Myth: no reply to ping = broken. Some hosts deliberately don't respond to ping.
  • Mistake: blaming the provider right away. First check your own side (address, gateway, DNS).
  • Myth: if 8.8.8.8 responds to ping but sites won't load — "the internet is broken." This is a classic sign of a DNS problem.
  • Mistake: skipping the settings step. Often the root cause is simply a wrong address or gateway.

Frequently asked questions (FAQ)

  • A host isn't responding to ping — is it definitely broken? No, it might just be blocking ping.
  • Where do you even start? At the bottom: the cable/Wi-Fi and your own settings.
  • How do you know whether to fix it yourself or call the provider? Via traceroute: is the break on your end or further along.
  • What is ping -t? A continuous ping for catching "intermittent" drops.
  • Why can't you change everything at once? You won't know what actually helped.

Lab work

Part A. Run diagnostics on your own network

  1. Check your own settings: ipconfig (Windows) or ip addr (Linux/Mac).
  2. Ping in order: gateway → external IP 8.8.8.8 → the site by name.
  3. Determine at which step the problem would be if 8.8.8.8 responded to ping, but the site by name did not.

Part B. Read a traceroute

  1. Run tracert (or traceroute) to any site.
  2. Find your router (the first hop) and determine the total number of hops.
  3. Mark where the provider's network begins, and where the "outside world" begins.

Part C. Fix a fault in the simulator

  1. In Packet Tracer, take your network from module 5.
  2. Break one thing (for example, remove the gateway on a PC or set a wrong DNS).
  3. Run diagnostics step by step and find where the connection breaks.
  4. Fix the fault and confirm recovery with the ping command.

Part D. Build your own algorithm

  1. Write up a "6 steps of network diagnostics" reference sheet in your own words.
  2. Add to each step the command used to check it.

Additional labs

Part E. Continuous ping

  1. Run ping -t 8.8.8.8 (or without a count on Linux) for a couple of minutes.
  2. Assess stability: is there loss and are there spikes in time.

Part F. Diagnostic scenario

  1. Ask someone (or do it blind yourself) to introduce a fault into the network simulator.
  2. Find it strictly using the "bottom-up" method, recording each step.
  3. Write up a mini-report: what you checked, where the break was, what you fixed.
